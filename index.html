1   The problem

A digital chip goes through a sequence of physical-design stages — floorplanning, placement, clock-tree synthesis, routing. Each stage produces an estimate of the design’s final quality: how much area it will occupy, how much power it will draw, whether it will meet timing. Those early estimates are what a designer steers by.

They are also wrong, and they are most wrong exactly when they matter most. At floorplan — the point where changing course is cheapest — the OpenROAD estimate of total area is off by 12–22% depending on the technology node, and its estimate of worst slack is off by more than the slack itself. By the time the estimate is accurate, the design is routed and the expensive decisions are already made.

The question this benchmark asks: can a machine-learning model, given only the information available at an early stage, predict the final post-route value more accurately than the EDA tool’s own estimate at that same stage?

2   Goals of this leaderboard

  • Make ML-for-EDA comparable. Published work in this area uses commercial tools, proprietary PDKs and unreleased netlists, so results cannot be checked against each other. Everything here runs on open tools, open PDKs and a public dataset.
  • Give a baseline that is honest and hard. The comparison is against the tool estimate at the same stage, taken from the EDA-Schema-V2 paper rather than re-derived. A model does not “win” by beating a straw man.
  • Show where the problem is actually open. Not every cell is a research opportunity. At global route the tool is already exact for ten of twelve tasks. Marking those honestly is more useful than pretending the whole matrix is contested.
  • Make submissions cheap. Results folders are ingested exactly as they come off the cluster. No metadata file to write, no format to conform to.

3   How a prediction task is defined

A task is a triple: what you predict, from which stage, and on which PDK. All twelve tasks predict the value at detailed_route — the final stage — from an earlier one.

DimensionValues
Tasks12 — circuit-level (area, power, wirelength), net-level (interconnect length), timing (arrival time, slack, TNS), path-level and arc-level
PDKs4 — NG45, SKY130, IHP130, ASAP7
Stages5 — floorplan, global place, detailed place, CTS, global route
Circuits18 IWLS’05 designs, 108 parameter configurations each
Metric rows46 — metrics differ by task

That gives 232 live task–PDK–stage combinations and 880 scoreable cells.

4   The baseline you have to beat

Every number in the baseline row comes from Table 8 of the EDA-Schema-V2 paper: the error of the OpenROAD estimate at that stage against the final routed value, averaged across the dataset. It is not a model. It is what the tool already tells you for free.

A cell turns green when at least one submitted model has lower error than that figure, and red when none does. The bar behind each value in the table shows performance relative to the best and worst model in that column.

5   Metrics and why there is no single score

Each task carries the metrics that are meaningful for it, following the paper. Circuit-level tasks use MAE, MAPE and R². Long-tailed quantities such as interconnect length add 95th-percentile and top-5% variants, because the few long wires matter more than the many short ones. Slack-based tasks drop MAPE entirely — slack clusters near zero, so percentage error explodes — and add directional metrics instead.

MetricDirectionMeaning
MAElowerMean absolute error, in the metric’s own units
MAPElowerMean absolute percentage error
R²higherVariance explained; unstable when the target barely varies
MPE / MNElowerMean over-estimate and under-estimate, reported separately. For timing, over-estimating delay is safe; under-estimating hides a violation
TPR / TNRhigherHow often a violating or clean endpoint is correctly identified

There is deliberately no aggregate score. Averaging MAE against TPR against R² would require weights nobody can justify, and it would let a model with a catastrophic R² hide behind a good MAE. Every metric is ranked independently. A model that wins one column and loses another is showing you something real, and the table is built so you see both at once.

StateMeaning

GreyNo submission yet
◆ SaturatedThe tool estimate already equals the final value — error is exactly zero and no model can improve on it. This is the case at global route for ten of the twelve tasks, 132 cells in total
no ± errorMPE and MNE are undefined because there are no over- or under-estimates left to average. 24 cells
n/aNot estimable at that stage. Wirelength has no meaning before placement. 40 cells

Saturated cells are still browsable but are never ranked and never counted as wins. The live research frontier is floorplan, global place and detailed place.

7   Divisions and verification

Closed uses the canonical leave-one-circuit-out split, the canonical feature set and the canonical target — any architecture, but a controlled setup. Open is anything else, documented. Division is derived from the submission’s own directory structure rather than declared, so it cannot be mis-stated.

TierWhat it means
○ self-reportedPassed automated validation: feature-stage legality, split-overlap check, runnability smoke test, plausibility envelope
✓ verifiedA maintainer re-ran the model and reproduced the numbers
⚠ flaggedAn automated check raised a concern; results are shown with the warning attached rather than hidden

The strongest guard is feature-stage legality. Because EDA-Schema-V2 declares the stage at which every attribute becomes available, a submission claiming to predict from floorplan while reading a post-route attribute is rejected mechanically. No other ML-for-EDA benchmark can do this.

8   Known limitations

  • One submission is real; the rest are synthetic. Baselines are real, and the fixed_mlp row under Total area is the lab’s own sweep — 20 (PDK, stage) configurations, 18 per-circuit models each, read straight out of the run tree. Every other model on this page is placeholder data for interface review.
  • The real submission is undertrained, and the page says so. 25 epochs at 50 gradient steps leaves the checkpoints statistically at initialization; the explorer shows the evidence rather than hiding it. Its leaderboard numbers are still the numbers the lab measured.
  • Yosys is weaker than commercial synthesis. Results are reported per tool so gains attributable to the synthesis gap are not mistaken for modelling gains.
  • No hidden test set yet. Until one exists, contamination is guarded procedurally rather than structurally.
  • R² is fragile here. Where the target has almost no variance across the evaluation set, R² goes sharply negative and says more about the data than the model. The paper thresholds these at <-1 and so do we.
